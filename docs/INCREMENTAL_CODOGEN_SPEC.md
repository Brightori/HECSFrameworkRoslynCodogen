# Спека: инкрементальная запись генерата

> Статус: согласовано, к имплементации. Продолжение [SPLIT_CONTAINERS_SPEC.md](SPLIT_CONTAINERS_SPEC.md).

## 1. Принятая схема

**Читаем всё — записываем только изменённое.**

```
1. Парсим все .cs целевого проекта          (как сейчас, полностью)
2. Строим графы типов                        (как сейчас)
3. Генерируем ВСЕ выходные файлы в памяти    (дёшево: string building)
4. Перед записью сравниваем с диском:
      содержимое совпало  → файл НЕ трогаем
      отличается / нет    → записываем
5. ~~Ничего не удаляем~~ ⟶ удаляем осиротевшие файлы в директориях генерата (§3, решение изменено 2026-09-25)
```

Никакого состояния между прогонами: ни манифестов, ни git-якорей. Единственный источник истины — полный проход по исходникам; диск и компилятор видят только реальные изменения.

### Почему так (сводка стоимостей)

Масштаб для оценки: ~800 типов → ~800 файлов генерата, ~5 МБ текста.

| Операция | Стоимость |
|---|---|
| Генерация всех файлов в памяти | ~десятки мс |
| Чтение 800 файлов для сверки | ~50–100 мс |
| Запись только изменившихся (обычно 1–5) | ~мс |
| **Рекомпиляция Unity после изменения 800 файлов** | **десятки секунд — минуты** |
| Рекомпиляция Unity после изменения 2 файлов | секунды |

Дорогая строка — рекомпиляция потребителя, и её убирает сверка перед записью. Вся более сложная машинерия (выборочная генерация) играет в диапазоне ~100 мс и бюджет сложности не окупает.

Ключевое свойство схемы: **в ней нечему ошибаться**. Нет детектора изменений — нет и класса багов «протухший выход из-за неверной инвалидации». Изменение базовой системы, интерфейса, partial-части в другом файле — всё пересчитывается автоматически, потому что пересчитывается всегда всё.

## 2. Реализация записи

```csharp
private static void SaveToFile(string name, string data, string pathToDirectory, ...)
{
    var path = pathToDirectory + name;

    try
    {
        if (!Directory.Exists(pathToDirectory))
            Directory.CreateDirectory(pathToDirectory);

        if (!forceRebuild && File.Exists(path) && File.ReadAllText(path) == data)
            return;                                   // байт-в-байт совпало — диск не трогаем

        File.WriteAllText(path, data);
    }
    catch
    {
        Console.WriteLine("we cant save file to " + pathToDirectory);
    }
}
```

Требование к генераторам: вывод должен быть **детерминированным** (стабильный порядок обхода коллекций при построении текста), иначе сверка будет ложно срабатывать. Сейчас порядок задаётся порядком словарей/списков `Program.*` — при равных входах он воспроизводим; при изменении набора файлов допустимы единичные ложные перезаписи, это не ошибка.

Сверка применяется ко **всем** выходам: контейнеры типов, резолверы, blueprint'ы, `CommandsMap.cs`.

## 3. Удаление файлов

> ⟶ **Изменено 2026-09-25 (решение пользователя):** обычный прогон удаляет осиротевшие файлы. После записи из `Containers/`, `Resolvers/`, `FastComponentsProviders/` удаляются все `.cs` (с `.meta`), которых этот прогон не породил; в прогоне с `no_resolvers` чистится только `Containers/`, а `*FastContainer.cs` / `*ResolverContainer.cs` не трогаются. Набор «своих» файлов — то, что прогон поставил в очередь записи (`pendingFiles`), состояния между прогонами не хранится. Ниже — исходная формулировка.

Обычный прогон **никогда ничего не удаляет**. `CleanDirectory` для `Resolvers/` из обычного пути убирается (заменяется той же сверкой перед записью).

Последствие, принятое осознанно: удаление/переименование типа оставляет осиротевший файл (контейнер/резолвер), ссылающийся на несуществующий тип → **ошибка компиляции в целевом проекте**. Это рабочий сигнал: «удалил тип — прогони `force_rebuild`».

## 4. Флаг `force_rebuild`

Новый аргумент CLI (в `CheckArgs`, рядом с существующими):

```
RoslynHECS.exe path:... force_rebuild
```

Семантика:

1. очистить директории, целиком принадлежащие генератору: `Containers/`, `Resolvers/`, `FastComponentsProviders/`;
2. сгенерировать и записать всё без сверки.

~~Это единственный механизм удаления осиротевших файлов~~ ⟶ сироты удаляются и обычным прогоном (§3); флаг остаётся универсальным выходом при любых сомнениях в консистентности (обновление генератора, ручные правки генерата, битые файлы).

## 5. Смена флагов запуска

Набор флагов (`no_commands`, `no_resolvers`, `server`, …) влияет на содержимое генерата (например, `no_commands` меняет тела Bind сетевых интерфейсов). Схема самокорректируется: при смене флагов изменившиеся файлы честно перезапишутся при следующем прогоне. Прогоны с чередующимися наборами флагов будут «мигать» одними и теми же файлами — это ожидаемое поведение, не баг.

## 6. Отвергнутые альтернативы (и почему)

| Вариант | Причина отказа |
|---|---|
| **Выборочная генерация по git** (якорь-коммит, `diff --name-only`, порог) | Экономит ~100 мс генерации/сверки при цене: git-вызовы (~50–300 мс), файл-стамп, и три класса дыр — откат незакоммиченной правки после генерации (недо-инвалидация), смена флагов/версии генератора невидима для гита, сабмодули приходят одним гитлинком. Чинится всё, но бюджет сложности тратится на нулевой выигрыш |
| Порог «N коммитов → full» | Число коммитов не коррелирует с объёмом изменений (1 коммит-переименование = 500 файлов; 10 коммитов = 3 файла). Правильная метрика — число изменённых файлов, и она бесплатна (длина списка diff), но при отказе от git-схемы вопрос снят |
| Автоматический orphan-sweep (удаление файлов исчезнувших типов каждый прогон) | ⟶ **Принят 2026-09-25** (см. §3). Исходно: решение пользователя — обычные прогоны не удаляют ничего; удаление — только явное, через `force_rebuild` |
| **Манифест с инвентарём типов** (stat+hash по файлам, графы из инвентаря, парсинг только изменённых) | Корректная конструкция без git-дыр, но требует расслоения модели генератора (инвентарь / полный синтаксис) и режима «доверяем диску для незатронутых». Отложено как уровень 2 — см. §7 |

Гиту остаётся роль, где он бесплатен и не может навредить: **триггер** (хук после pull/checkout запускает генератор) и **CI-гейт** (`git diff --name-only base..head` — решить, нужен ли прогон вообще). Худшая ошибка там — лишний прогон, который сверка превращает в no-op.

## 7. Уровень 2 (отложено): кеш парсинга

Единственная фаза, которую текущая схема не ускоряет — парсинг (секунды на тысячах файлов). Если замеры покажут, что это болит, поверх схемы ложится манифест:

- на файл: `size + mtime + contentHash` + **инвентарь типов** (имя, kind, partial, base-list строками);
- графы строятся из инвентаря без парсинга; парсятся только изменённые файлы + окружение затронутых типов (родители, parts, интерфейсы);
- генерируются только затронутые контейнеры, остальным доверяем диску;
- любое несоответствие (версия, флаги, битый манифест) → полный проход.

Требует рефакторинга: `LinkedNode` и графостроение переводятся на строковый инвентарь, Roslyn-ноды гидрируются лениво. Не начинать без замера: обернуть фазы (парсинг / графы / генерация / запись) в `Stopwatch` и посмотреть реальные цифры на боевом проекте.

## 8. Порядок внедрения

1. Вместе с контейнерами ([SPLIT_CONTAINERS_SPEC.md](SPLIT_CONTAINERS_SPEC.md)): сверка перед записью в `SaveToFile`, удаление `CleanDirectory` из обычного пути, `force_rebuild` в `CheckArgs`.
2. Замер фаз секундомером, вывод таймингов в консоль при каждом прогоне.
3. Уровень 2 — только по результатам замера.
